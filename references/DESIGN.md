# 业务语言持续学习：需求与设计

> 这份文档说明「为什么这么设计」。执行采集、脱敏或盲测前必须完整读一遍——
> 里面每一条边界都对应一次真实的翻车。

## 1. 目标

把“懂业务语言”从模型感觉变成可追溯、可积累、可校验的写作能力，同时保留作者判断、真实场景和表达生命力。

系统必须形成以下闭环：

> 采集 → 识别业务表达 → 保留来源 → 辅助写作 → 分级检查 → 收集反馈 → 更新词包、案例与作者偏好

默认采用**影子模式**：只提示和学习，不阻断定稿，不静默替换原文。

## 2. 核心原则

### 2.1 业务证据与写作表达分层

- 业务证据层约束产品名、业务对象、事实、指标和核心业务主张。
- 写作表达层允许调整叙事顺序、节奏、转场、动词、情绪和详略。
- 校验发生在成稿之后，不把内部检查框架直接写成页面结构。

### 2.2 通用机制与分业务词包

- 通用规则只保存跨业务稳定成立的写作方法（`language-packs/common.yaml`）。
- 每个业务域拥有独立词包；一份材料可自动加载多个词包。
- 同一词在多个业务域出现时建立引用，不复制出互相冲突的定义。

### 2.3 来源可追溯

来源可信度依次为：

1. owner 明确确认；
2. 已被采纳或正式使用的材料；
3. 正式业务文档、会议纪要和产品名称；
4. 已通过评审的历史版本；
5. 聊天记录和普通工作材料。

**第五类来源只能自动成为候选，不能仅凭高频转为正式业务词。** 这一条是整套设计的地基：聊天里说得最多的词，往往正是最没被推敲过的词。

### 2.4 活人感持续进化

活人感来自真实人物、任务、动作、变化与作者取舍，不来自口头禅或固定金句。系统保存完整反馈事件：原表达、修改后表达、原因、听众、场合、表达目标和结果，并从中提炼场景化原则。

## 3. 用户与场景

### 3.1 主要用户

- 季度会、年度会和管理层汇报的材料作者；
- 面向一线团队的宣讲者；
- 周报、复盘和跨团队方案的撰写者；
- 执行写作、校验和学习流程的 AI Agent。

### 3.2 典型场景

1. 写作前按主题自动加载通用词包和相关业务词包。
2. 写作时检索业务对象、动作、交付物、固定搭配和真实句式。
3. 成稿后按标题、核心主张、章节总结和正文分级提示。
4. 用户确认或否定表达后，自动生成反馈事件并更新候选知识。
5. 高价值材料生成匿名评测包，交给多个模型独立评价。
6. 外部公开材料只补充写法，不进入内部业务词库。

## 4. 功能需求

### FR-1 业务词包

每条记录至少包含：稳定 ID、标准表达、类型、业务域、状态、适用听众、适用位置、释义、变体、来源与证据等级。

状态流转：`candidate → supported → pending_confirmation → approved/rejected`。
只有 owner 确认、已采纳稿或正式命名可以直接进入 `approved`。

### FR-2 自动路由

根据文件路径、标题、产品名和正文特征自动选择词包，允许多词包叠加。路由结果必须说明命中的证据。

### FR-3 分级检查

检查位置分为：

- `title`：标题；
- `claim`：核心主张和关键结论；
- `summary`：章节总结、带走句和行动要求；
- `body`：事实描述、转场和普通口播。

默认全部输出提示，不返回阻断退出码。每条提示包含：位置、问题、触发原因、可参考的业务表达和来源。

### FR-4 业务语言四层积累

同时积累：① 业务词；② 固定搭配；③ 真实句式；④ 正反案例。
**不得只依靠逐词命中判断材料质量。**

### FR-5 增量采集

- 允许配置可信来源、可信人员和主题搜索词；
- 记录消息来源、时间、说话人匿名标识和上下文；
- 自动抽取候选表达并归入候选区；
- 高频只提高证据等级，**不自动转正**；
- 采集源不可用时使用缓存并明确说明本次未更新。

采集适配层与写作内核分离：内核只接受 `content / source / timestamp / speaker` 结构的 JSONL，不关心它从哪来。

### FR-6 反馈学习与作者档案

- 支持写入显式纠正、版本选择、最终结果和真实业务表达；
- 一次反馈只影响相似场景；重复偏好可升级为作者偏好；明确原则进入稳定规则；
- 冲突反馈按听众和材料类型并存，**不直接覆盖**；
- 作者档案独立版本化并支持回退；
- 重复套用相同金句时给出模板化提示。

### FR-7 一致性脱敏

- 同一实体在全文稳定映射；不删句、不打乱章节、不改变关系和因果；
- 可配置敏感数字等比例变换；
- 映射与脱敏稿按内容摘要缓存，内容未变时复用；
- **映射表与脱敏稿只保存在本地，不进入语料库，不进入版本库。**

### FR-8 多模型匿名评价

- 三个角色：合成（出候选稿与综合）、逻辑（查矛盾、理解断点、模板化）、挑战（独立反对意见）；
- 所有模型按同一组问题输出，**不显示模型名称**；
- **不用多数投票决定文案**；模型意见只作为候选反馈；
- 仅高价值材料默认启用三模型评价。

### FR-9 外部写作参考

- 只学习判断组织、详略选择、场景叙事、节奏、数字论证和标题写法；
- 外部材料与内部业务词库**物理分开**；
- 每条参考记录来源、适用场景、学到的方法和边界；
- **热门概念不得自动进入业务词包。**

**实现**（`techniques/*.yaml` + `extract_technique_candidates`）：

字段：`id / title / category / problem / technique / example_before /
example_after / use_when / avoid_when / source / status / promotion`。

三条硬约束：

1. **必须有 `example_before` / `example_after` 对照。** 没有对照的技巧是抽象口号——
   这是这条 FR 最早失败的地方。
2. **必须有 `avoid_when`。** 任何手法用错场合都会变成毛病；只说"该用"不说"别用"等于教人滥用。
3. **`source.kind: external` 的条目永远 `status: candidate`**，且一律 `promotion: forbidden`，
   不论被引用多少次。

⚠️ **工具只定位候选，不生成技巧。** `extract_technique_candidates` 认四类对照结构
（`contrast` / `before_after` / `number_reading` / `myth_break`），输出带 `excerpt` 的骨架，
`title / problem / technique / avoid_when` 四项留 TODO。
理由：这四项是**判断**，正则产不出判断。早期版本让外部资料走业务名词正则，
抽出来全是「XX方法」「XX能力」——看着像结果，实际没有可复用信息。
补全交给人或模型，工具负责把「值得看一眼的段落」从长文里挑出来。

### FR-10 兼容现有检查器

`style-lint` 与 `rewrite-check` 与本内核读取同一份规则源，正式名称优先于通用禁词。版本号不得当成新增业务数字。旧命令入口继续可用。

### FR-11 本地知识检索

- 可信来源配置、脱敏消息、候选表达和已确认知识必须分层保存；
- 默认只检索 owner 已确认或正式材料支持的知识卡，原始聊天仅用于追溯；
- 每张知识卡至少包含主题、核心判断、适用场景、业务动作、表达边界和来源等级；
- 检索结果必须返回来源，不能只给脱离语境的句子；
- **无需联网、无需向量服务**，使用可解释的关键词检索；没有命中时明确返回未命中；
- 可信来源、脱敏语料，以及从个人聊天推导出的偏好、判断和共识**均只在本地保存，不进入 Git**；
- pre-commit 必须检查暂存区：本地私密路径、聊天扫描产物、聊天记录结构、个人评价标记任一命中即阻断提交，并提示迁移到 `.runtime/`。

### FR-12 场景化反馈复用（v2.0）

反馈事件必须保存 `before / after / reason / audience / material_type / topic / reuse_scope / result / source.kind`，并带 schema 版本与 UTC 时间。反馈仍然是可追溯事件，不直接改写业务词包或作者档案。

写作前通过 `feedback-query` 检索当前场景：

- `once`：只留档，不参与后续写作；
- `similar`：听众和材料类型必须一致，主题或反馈证据必须与当前任务有可解释的关键词重合；
- `stable`：用于 owner 明确确认的长期原则，仍受听众和材料类型约束；如需跨场景，由调用方明确传入 `all`，不做隐式扩散；
- 非 owner 反馈不进入可复用结果；
- 同一 `before` 在当前场景出现多个不同 `after` 时，全部进入 `conflicts`，从 `applicable` 移除，不自动覆盖或选边；
- 查询结果必须返回匹配词和分数，便于追溯为什么命中。
- 成稿后通过 `feedback-check` 验证命中的 `before` 未复发；本稿未涉及该表达时不强制加入 `after`，回归或存在冲突时返回非零。

Skill 在每次写作前主动执行检索，不要求用户先填作者卡。用户反馈发生后再记录，学习是正常写作的副产品，不是前置任务。

## 5. 非功能需求

- 仅使用 Python 标准库与 PyYAML；**无网络时全部核心能力可运行**。
- 所有自动判断保留证据，不以不可解释的总分替代具体问题。
- 稳定资产可版本管理；运行缓存、原始聊天和脱敏映射不得提交。
- 单文件检查在普通汇报材料上应在 2 秒内完成。
- Skill 主入口保持精简，详细结构和字段说明按需加载。

## 6. 验收标准

1. 已采纳稿中的正式产品名不被误报。
2. 旧版本中的无来源抽象概念可被提示。
3. 标题中新增无来源业务概念时产生高优先级提示，但默认不阻断。
4. 普通自然语言不会因词库未收录而被大量误报。
5. 新增确认反馈后，再次扫描能读取这条知识。
6. 脱敏后章节数、行数、实体关系和非敏感数字保持一致。
7. 只有指定角色能拿到原稿，其余角色一律拿脱敏稿。
8. 多模型结果使用匿名候选标识，并保留各自评价依据。
9. 外部参考不能被业务词路由器加载为内部标准词。
10. Python 单测与真实材料对照测试全部通过。
11. 外部来源的技巧条目在任何路径下都不会变成 `approved`，也进不了业务词包。
12. `once` 反馈、其他听众和其他材料类型的反馈不会串入当前材料。
13. 同一场景的 owner 反馈能在下一次写作前被检索，并返回匹配依据。
14. 冲突反馈完整保留且不进入自动应用列表。
15. 非 owner 来源即使填写可复用结果值也不会被复用。
16. 下一稿若仍出现旧表达，`feedback-check` 验收失败；未涉及该表达时不会误报。

## 7. 明确不做

- 不建设图形化后台；使用可读 YAML、JSONL 和命令行报告。
- 不让模型意见自动转为稳定规则。
- 不让聊天高频表达自动转为正式业务词。
- 不默认启用硬阻断；先积累真实误报、漏报和采纳反馈。
- 不主动联网抓取；采集适配器由调用端提供。
